# B 파트 AGENTS 규칙 (여행·일정·공동 작업)

공통 `AGENTS.md`를 먼저 따른다. 이 파일과 부딪히면 공통 규칙이 우선이다.
세부 동작은 세부기능정의서 v33의 해당 기능 ID 행을 그대로 따른다.

## 1. 담당 범위

### 기능 (25개)
- 여행 관리: TRP-01-01 기본정보 입력·검증, TRP-01-02 도시 검색·선택, TRP-01-03 여행 생성 저장, TRP-02-01 내 여행 목록·검색, TRP-02-02 상세 진입·권한 재확인, TRP-02-03 메인 화면, TRP-03-01 여행 정보 수정, TRP-03-03 기간 변경 확정, TRP-05-01 삭제(휴지통), TRP-05-02 휴지통 목록, TRP-05-03 복원, TRP-05-04 만료 영구 삭제, TRP-05-05 휴지통 비우기·개별 영구 삭제
- 일정 관리: SCH-01-01 날짜별 시간표 조회, PLC-05-01 공동 후보 추가·삭제, PLC-05-02 후보 목록·배치 상태, PLC-05-03 필수 방문 표시, SCH-02-01 방문 일정 추가·삭제, SCH-03-01 순서 변경, SCH-04-01 날짜·방문시간·체류시간 수정, SCH-04-02 날짜·시간 고정, SCH-05-01 메모, SCH-06-01 일정 변경 저장
- 공동 작업: COL-06-01 저장 내용 전파·동기화, COL-06-02 동시 수정(나중 저장 우선)

### 폴더
- 백엔드: `com.planmate.trip`, `com.planmate.schedule`, `com.planmate.collab`
- 프론트: `features/trip`, `features/schedule`, `features/collab`

### 테이블
- 여행(TRIP), 일차(TRIP_DAY), 공동 후보(TRIP_CANDIDATE), 방문 항목(VISIT), 메모(VISIT_MEMO), 영구 삭제 기록(PURGE_LOG)
- 도시(CITY): B가 주인(trip/), C는 CityService로 사용
- 요청 기록(REQUEST_LOG): `common/duplicate`에 있음. B가 처음 설계했지만 공통 파일이라 고칠 때 팀 공유
- 여행 참여자(TRIP_MEMBER)는 A가 주인. B는 ParticipantService로만 쓴다.

## 2. 여행 규칙

- 생성 개수: 참여 중인 활성 여행 최대 3개(소유·편집·조회 모두, 넘겨받은 여행·복제한 여행 포함, 휴지통·참여 끝난 여행 제외). 개수 확인과 생성은 한 번에 처리해 동시에 두 번 요청해도 4번째가 생기지 않게 한다.
- 제목: 앞뒤 공백 제거 후 1~50자, 공백만 불가. 특수문자·이모지 허용, 제어문자 불가(붙여넣기로 들어오면 공백 1칸). 화면에는 HTML로 해석하지 않고 글자 그대로 표시.
- 도시: 1개, 생성 후 변경 불가. 전 세계 도시 자유 선택, 처음 고른 도시는 CITY에 자동 등록. 국내는 KAKAO, 해외는 GOOGLE(CITY.MAP_PROVIDER), 한 여행 안에서 섞지 않음.
- 도시 검색: 구글 장소 자동완성(도시+국가), 시간대는 구글 시간대 API. 구글 호출은 C의 client를 거친다. 입력이 멈추고 0.3초 뒤 검색, 결과 최대 3개.
- 기간: 실제 있는 날짜, 종료일 >= 시작일, 일수(종료일 - 시작일 + 1) 1~7일. 시작일은 여행지 현지 오늘 ~ 1년 후(다음 해 같은 날짜). 여행 정보 수정에서 시작일을 안 바꾸면 범위 검사 안 함.
- 인원: 정수 1~20, 참여자 수와 상관없이 입력값 그대로 저장.
- 생성 처리: TRIP 1행(STATUS=ACTIVE) -> 생성자를 OWNER로 등록(A의 ParticipantService) -> 일수만큼 TRIP_DAY 생성. 같은 요청 식별값이면 새로 만들지 않고 기존 결과를 돌려준다. D의 공개 여행 복제도 이 기능을 쓴다(개수 제한 같음).
- 목록: 현재 참여 중인 활성 여행만. 탭 [전체] [다가오는 여행](종료일 >= 현지 오늘, 진행 중 포함) [지난 여행]. 만든 시각 내림차순 -> 여행 ID 내림차순, 10개씩 무한 스크롤(마지막 여행 기준으로 이어 받기). 검색 1~50자, 제목·도시명(한글·영문) 부분 일치, 대소문자 무시, 메모 제외, 탭 조건과 AND. 제목 옆에 "n/3".
- 상세 진입: 열 때마다 TripAccessChecker로 권한 재확인.
- 정보 수정(소유자·편집 참여자): 제목·인원은 바로 저장. 인원이 바뀌면 D에 알려 경비를 다시 계산하게 한다(계산은 D).
- 기간 변경: 확인 창에서 [변경]을 눌러야 저장. 날짜만 옮기고 일수가 같아도 모든 방문 항목을 일정에서 뺀다. 장소는 공동 후보에 남고, 고정은 풀리고, 메모는 방문 항목과 함께 삭제한다(11/23 결정, 후보 보관 메모 없음). TRIP_DAY를 새 기간에 맞춘다.
- 삭제(소유자만): STATUS=TRASHED, DELETED_AT 기록, 휴지통 7일(168시간). 참여자 접근 막음, 초대 링크 폐기(A), 공개 게시물 노출 중단(D), 삭제 알림 저장(A, 문구: "'{여행 제목}' 여행이 삭제됐어요. 소유자가 복원해도 다시 초대받아야 참여할 수 있어요.").
- 복원(소유자, 이용 제한 회원도 가능): 영구 삭제 예정 시각 전까지만. 삭제 직전 공개 상태 그대로(D). 소유자 외 참여 관계는 모두 삭제(A). 복원 알림 없음.
- 영구 삭제: job이 하루 1번, 대상은 TRASHED이고 현재 시각 >= 삭제 시각 + 7일. 복원 가능 여부는 job 주기가 아니라 예정 시각 기준. 탈퇴로 삭제한 여행은 빼고 A가 2주 뒤 회원 삭제 때 처리. 실패는 PURGE_LOG에 남기고 다음 실행 때 다시 시도. 영구 삭제 뒤 백업·로그에 여행 데이터를 남기지 않음. 다른 회원이 이미 복제한 여행은 지우지 않음. 휴지통 비우기·개별 영구 삭제도 같은 순서.

## 3. 후보·일정 규칙

- 공동 후보: 같은 장소(제공자 + 장소 ID) 여행당 1개, 최대 100개, 여행 도시와 같은 지도 제공자 장소만. 추가·삭제·필수 표시는 누르는 즉시 저장(일정 저장과 별개). 후보 ID 내림차순. 시간표에 그 후보로 만든 방문이 있으면 삭제 불가("이 장소의 일정이 시간표에 있어서 후보에서 삭제할 수 없어요. 시간표에서 일정을 먼저 삭제해 주세요.").
- 장소 정보는 C의 공통 장소 형식으로 받는다. 구글 장소는 장소 ID만 오래 저장하므로 이름·주소·좌표·카테고리가 비어 있을 수 있다(NULL 허용).
- '내 보관함에서 불러오기'는 A의 SavedPlaceService 목록을 쓴다(같은 지도 제공자 장소만, 이미 후보면 '추가됨'). 후보에 넣어도 보관함은 바뀌지 않는다.
- 배치 상태: 그 후보로 만든 방문이 시간표에 있는지(0개면 흐리게).
- 시간: 여행지 현지 날짜·시각, 시간대 변환 없이 저장. 방문시간은 VARCHAR2(5) "HH:mm"(24시간) 00:00~23:55, 5분 단위.
- 일정 추가: 후보 카드 [...] > [일정에 추가] -> 일차 선택 -> 그날 마지막 일정 뒤. 방문시간 기본값 = 그날 마지막 종료시각을 5분 단위로 올림(없으면 09:00, 23:55 넘으면 23:55). 체류시간 기본값 = C의 권장 체류시간(없으면 30분).
- 체류시간 10~720분, 5분 단위. 하루 방문 최대 25개. 같은 장소 반복 방문 허용.
- 종료시각이 24:00을 넘어도 저장하고 경고만. 시간 겹침([방문시간, 종료시각)이 1분 이상)·이동시간 부족·활동시간(기본 09:00~22:00) 초과도 확인 창 없이 저장하고 경고만.
- 순서 변경(드래그만, 같은 날짜 안): 옮긴 항목만 앞 항목 종료시각으로 바꾸고 다른 항목 시간은 그대로. 체류시간을 늘려도 뒤 항목을 밀지 않는다.
- 고정: VISIT.PIN_TYPE = NONE / DATE / TIME(방문시간+체류시간). 고정 항목은 풀어야 수정·삭제 가능, 풀기와 수정은 한 번에 저장 가능.
- 메모: 방문 항목당 1개(VISIT_MEMO), 1~1,000자, [완료]·[삭제] 누르면 저장(일정 저장 경로 사용). 열람은 참여자 전원, 작성은 소유자·편집 참여자. 방문을 지우면 메모도 삭제. 탈퇴자가 소유자면 메모 삭제, 편집 참여자면 내용 유지하고 이름을 '탈퇴한 회원'으로(A가 호출).

## 4. 일정 저장 (SCH-06-01, ScheduleSaveService)

- 저장 버튼 없음. 편집 동작 1건마다 바로 저장. AI 적용(C)·복제(D)처럼 여러 변경은 한 번에 저장. 별도 저장 경로를 만들지 않고 모두 ScheduleSaveService를 탄다.
- 서버 검사: 로그인, 여행 ACTIVE, 요청 시점 역할이 OWNER·EDITOR, 형식, 고정. 한 번에 보낸 변경 중 하나라도 권한·형식·고정 오류면 전체를 저장하지 않는다(일부만 저장 금지).
- 다른 참여자가 먼저 바꾼 항목도 내 값으로 덮어쓴다. 저장한 VISIT·VISIT_MEMO 행은 VERSION을 직접 +1 한다(`@Version` 쓰지 않음, 덮어쓰기 판정에 쓰지 않음, 전파·AI 적용 확인용).
- 같은 요청 식별값은 한 번만 처리(DuplicateRequestChecker).
- 저장 성공 후에만: 다른 참여자에게 전파(COL-06-01) -> 새로 생긴 구간(출발 장소 -> 도착 장소) 목록만 C의 RouteService에 넘긴다.
- 이미 삭제된 항목 저장: "이미 삭제된 일정이라 저장할 수 없어요."
- 실패 안내 문구
  - 네트워크·서버: "저장하지 못했어요. (이유: 서버 연결이 끊겼어요)" [다시 시도] [닫기]
  - 권한 변경: "편집 권한이 바뀌어 저장할 수 없어요." (화면은 편집 불가로 바꾸고 최신 상태 다시 조회)
  - 형식: "확인이 필요한 일정이 n개 있어요. 아무 변경도 저장되지 않았어요."
  - 고정: "다른 참여자가 고정한 일정이 있어 저장하지 못했어요. 표시된 일정을 확인해 주세요."
- 화면: 실패한 동작만 원래대로 되돌린다. 어떤 실패도 저장된 것처럼 보이지 않는다. 성공 안내 메시지는 띄우지 않는다.

## 5. 변경 전파·동시 수정 (COL-06)

- WebSocket(11/05 결정). 서버는 `collab/websocket/TripSyncHandler`, 화면은 `shared/api/websocket.ts` + `features/collab/hooks/useTripSync.ts`. 서버 1대 기준(연결 목록은 서버 메모리).
- 주소·메시지 이름은 `contracts/collab.yaml`에 먼저 적고 그대로 쓴다(팀 공통 계약).
- 연결할 때와 보내기 직전에 받는 사람의 현재 참여 권한을 확인한다.
- 전파 대상: 일정, 기본정보(제목·인원), 기간, 공동 후보, 메모. 체크리스트(A)·경비(D)도 SyncService를 불러 전파한다. 목표: 저장 후 5초 안.
- 보내는 내용: 여행 ID, 바뀐 항목 종류·ID 목록, 바뀐 방문 항목·메모의 새 버전, 저장한 사람, 저장 시각. 저장된 것만 보낸다.
- 받는 화면: 내가 고치지 않은 항목은 바로 갱신. 내가 고치는 중인 항목(시간 선택·메모 입력칸을 연 상태)은 덮어쓰지 않고 점만 표시.
- 재연결: 1·2·4초... 최대 30초 간격. 다시 붙으면 권한 재확인 + 전체 최신 상태 다시 조회. 끊긴 동안의 편집은 저장 실패로 처리. 참여가 끝났으면 "이 여행에 더 이상 접근할 수 없어요." 후 내 여행 목록으로. 계속 실패하면 "연결이 불안정해요. 새로고침해 주세요."
- 바뀐 항목 점: 일정 변경 알림을 A의 NotificationService로 저장한다(TYPE=SCHEDULE_CHANGED, TARGET_TYPE=VISIT / CANDIDATE, 받는 사람 = 바꾼 사람을 뺀 활성 참여자). 점은 그 항목의 안 읽은 알림이 있을 때만 표시하고, 알림을 읽거나 [모두 읽음]을 누르면 사라진다(점을 눌러서는 안 사라짐).
- A의 알림 배지 실시간 갱신도 이 연결을 쓴다.
- 동시 수정: 나중에 저장한 값으로 덮어쓴다. 소유자 확인·대기·잠금·자동 합치기 없음.

## 6. 화면 표시 (B 화면 기준값)

- PC 기준 폭 1024px 이상, 일정 화면은 시간표 40% + 지도 60%(지도는 C의 MapView).
- 여행 화면 탭 [일정] [후보] [경비] [체크리스트], 처음엔 [일정]. 제목 옆 아이콘: AI 추천(C), 공유하기(D, 공개 중이면 비활성), 여행 설정.
- 여행 설정 창: 왼쪽 메뉴 [일반] [참여자 관리](A). [일반]은 여행 정보 수정(도시 칸 없음)·여행 삭제(소유자만)·여행 나가기(A).
- 날짜 2026.10.30(금), 여행 화면 안에서는 올해면 10.30(금). 기간 "2026.10.20(월) ~ 10.22(수) · 3일".
- 시간: 12시간제 "오후 02:05"로 표시, 입력은 [오전/오후]·시(01~12)·분, 저장은 24시간.
- 체류시간 "90분". 기록 시각: 오늘이면 "14:05", 아니면 "10.28", 올해가 아니면 "2025.12".
- 안내 메시지는 화면 아래 가운데. 성공은 3초 뒤 사라짐, 실패·연결 끊김은 닫을 때까지 유지. 불러오는 중은 회색 빈 카드 3개(스피너 쓰지 않음), 버튼은 비활성 + '...중'. 입력 오류는 칸 테두리 빨간색 + 칸 아래 빨간 글씨.
- 필수 방문: 장소명 앞 별(채워진 별 = 필수). 고정: 번호 왼쪽 위 압정 아이콘. 경고: 경고 항목과 날짜 탭을 구별되게(개수 없음). 바뀐 항목 점: 카드 오른쪽 위 테두리에 걸치게.

## 8. 문서끼리 다른 곳 (코드 쓰기 전에 사람에게 확인)

- 영구 삭제 방식: 기능정의서 TRP-05-04는 "각 파트의 여행 ID로 삭제 기능을 순서대로 호출 -> 마지막에 여행 삭제", DB설계서 v7은 "TRIP을 지우면 하위 데이터는 ON DELETE CASCADE로 함께 삭제". 단, NOTIFICATION은 TRIP_ID만 비우므로 A의 알림 삭제는 따로 불러야 한다.
- 기간 변경 때 메모: 기준값 '기간 변경 시 일정'과 TRP-03-03 기능 정의에는 "메모는 그 후보 장소에 보관"이 남아 있지만, '일정에서 빠진 방문의 메모'(11/23)와 DB설계서 v7은 "방문과 함께 삭제". 이 파일은 삭제로 적었다.
- 검색 결과에서 일정에 바로 추가: PLC-05-01·SCH-02-01에는 검색 결과 카드·상세의 [일정에 추가]가 있고, C 기준값 '검색 결과 버튼'에는 하트와 [후보에 추가]만 있다.
