# A 파트 AGENTS 규칙 (계정·참여자·운영·알림 + 원래 E 기능)

공통 `AGENTS.md`를 먼저 따른다. 이 파일과 부딪히면 공통 규칙이 우선이다.
세부 동작은 세부기능정의서 v33의 해당 기능 ID 행을 그대로 따른다.
원래 E 파트(장소 보관함·날씨·체크리스트·PNG·FAQ·1:1 문의)도 A 팀원이 구현하므로 이 파일에 넣었다. 기능정의서에는 아직 '담당 파트 E'로 적혀 있다.

## 1. 담당 범위

### 기능 (A 41개 + 원래 E 14개)
- 가입·로그인: ACC-01-01~04 이메일 가입·인증, ACC-02-01 로그인, ACC-02-02 로그아웃, ACC-03-01 소셜 인증·로그인, ACC-03-02 소셜 최초 가입
- 계정 관리: ACC-04-01 비밀번호 변경, ACC-04-02·03 비밀번호 재설정, ACC-05-01 닉네임·프로필 사진, ACC-05-02 집 주소, ACC-06-01 탈퇴 영향 조회, ACC-06-03 탈퇴 확정, ACC-06-04 소셜 연결 해제 (ACC-06-02는 없음)
- 공통 접근 제어: ACC-07-01 로그인·계정 상태, ACC-07-02 여행·개인 자료 접근, ACC-07-03 관리자 검사
- 여행 참여자: COL-01-01 초대 링크 발급, COL-01-02 폐기, COL-02-01 초대 접속·참여 확인, COL-02-02 참여 등록, COL-03-01 참여자 목록, COL-03-02 역할 변경, COL-04-01 나가기, COL-04-02 내보내기, COL-05-01 소유권 이전 요청, COL-05-02 수락, COL-05-03 취소·거절·만료
- 운영: ADM-01-01~04 회원 조회·이용 제한·해제·조치 이력, ADM-02-01~04 신고 목록·상세·처리·관리자 비공개 해제
- 알림함: SUP-03-01 조회·읽음, SUP-03-02 저장·보관 만료, SUP-03-03 대상·문구 판정
- 원래 E: PLC-04-01 즐겨찾기 저장·삭제, PLC-04-02 내 보관함 목록, SUP-01-01 날씨, SUP-02-01 체크리스트 목록, SUP-02-02 항목 추가·수정·삭제, SUP-02-03 완료 체크, SUP-02-04 개인별 체크리스트, SUP-04-01 일정표 PNG 저장, ADM-03-01 FAQ 보기, ADM-04-01 FAQ 관리, ADM-05-01 1:1 문의 등록·수정·삭제, ADM-05-02 내 문의 내역, ADM-06-01 문의 목록 관리, ADM-06-02 답변 등록·수정

### 폴더
- 백엔드: `com.planmate.auth`, `member`, `participant`, `notification`, `admin`, `common/security`, 원래 E의 `savedplace`, `weather`, `checklist`, `cs`
- 프론트: `features/auth`, `member`, `participant`, `notification`, `admin`, 원래 E의 `savedplace`, `weather`, `checklist`, `export`, `cs`
- `common/security`는 공통 폴더 안에 있지만 A 담당이다. 고치면 전체 파트에 영향이 있으니 팀에 먼저 알린다.

### 테이블
- 회원(MEMBER), 이메일 인증(EMAIL_VERIFICATION), 로그인 시도 기록(LOGIN_ATTEMPT), 탈퇴 처리 작업(WITHDRAWAL_JOB)
- 로그인 세션(SPRING_SESSION), 세션 속성(SPRING_SESSION_ATTRIBUTES): Spring Session JDBC가 관리. 엔티티 만들지 않음
- 초대 링크(TRIP_INVITE), 여행 참여자(TRIP_MEMBER, B도 사용), 소유권 이전 요청(OWNERSHIP_TRANSFER)
- 커뮤니티 이용 제한(MEMBER_RESTRICTION), 회원 정보 열람(MEMBER_VIEW_LOG), 신고·콘텐츠 조치(REPORT_ACTION), 알림(NOTIFICATION)
- 원래 E: 찜(SAVED_PLACE), 체크리스트(CHECKLIST_ITEM), 체크리스트 체크(CHECKLIST_CHECK), FAQ(FAQ), 1:1 문의(INQUIRY)
- 신고(REPORT)는 D가 주인. A는 D의 ReportService로 쓴다.

## 2. 계정 규칙

- 비밀번호(A-F01, A-P01): 8~64자, 영문·숫자·특수문자 모두 포함(대소문자는 같은 종류). ASCII 가시문자만(공백·한글·제어문자 불가). trim·대소문자 변환·잘라내기 금지, 초과값은 오류. 확인값과 완전 일치.
- 비밀번호 보관(A-P02): 적응형 단방향 해시(Spring Security PasswordEncoder). 원문은 저장·로그 금지, 화면 메모리에만.
- 닉네임(A-F02): 2~12자, 한글 완성형·영문·숫자·밑줄. 공백·이모지 불가, 중복 허용. 예약어(관리자, 운영자, admin, administrator, 운영팀) 영문 대소문자 무시 차단.
- 이메일(A-P03): 아이디와 도메인을 '@'로 합친 한 값. 앞뒤 공백 제거, 소문자 정규화(MEMBER.EMAIL_NORMALIZED), 최대 254자. + 별칭·마침표를 지우지 않음.
- 인증번호(A-F03, A-P04, A-P09): 6자리 숫자 문자열(앞자리 0 유지), 서버 난수. 용도 SIGNUP / RESET_PASSWORD. 5분 유효, 재발송 60초 뒤, 이메일당 시간당 5회·IP당 시간당 30회, 발급건당 오입력 5회면 폐기. 번호는 HMAC(CODE_HMAC)으로 보관하고 비밀키는 환경 변수. 인증 후 가입·재설정 확인값은 5분·1회.
- 재설정: 있는 이메일·없는 이메일에 같은 응답. 현재 비밀번호와 같은 값 금지.
- 로그인 제한(A-P06): 계정 기준 15분 안에 실패 5회면 15분 제한, 성공하면 실패 횟수 초기화. IP 기준 15분 50회는 초기안.
- 세션(A-P07, A-P08): Spring Security 서버 세션 + Spring Session JDBC, HttpOnly·Secure 쿠키. 일반 회원 무활동 60분·최대 12시간, 관리자 무활동 15분·최대 8시간. SameSite·CSRF·CORS는 배포 구조에 맞춰 검증(개발 중 프론트 주소 http://localhost:5173 허용, 쿠키 포함).
- 비밀번호 변경·재설정 성공: 그 회원의 모든 세션 종료(SPRING_SESSION.PRINCIPAL_NAME). 일반 로그아웃은 현재 세션만.
- 로그인 후 서비스 안의 허용된 주소로만 돌아간다. 하려던 동작을 자동으로 실행하지 않는다.
- 가입 후: 이메일 가입은 로그인 화면으로, 소셜 최초 가입은 로그인된 상태로.
- 소셜 로그인: 카카오·네이버·구글·Apple(MEMBER.PROVIDER = EMAIL / KAKAO / NAVER / GOOGLE / APPLE). 제공자마다 따로 계정(같은 이메일이어도 합치지 않음). 외부 호출은 `auth/client/OAuthClient`, state 값은 서버 세션에 저장. 소셜 회원은 서비스 비밀번호가 없다.
- 집 주소(ACC-05-02): 선택 입력, 카카오 우편번호 서비스 창에서 고름. MEMBER.ZIP_CODE·ADDRESS·ADDRESS_DETAIL. 본인만 조회, 관리자도 볼 수 없음. C의 나의 출발 안내(RTE-04-01) 처음 값으로 제공.
- 탈퇴(ACC-06): 단계는 소유 여행 정리 -> 확인 창 [다음] -> 최종 확인 창에서 '탈퇴하는 것에 동의합니다.'를 정확히 입력(서버도 확인) -> [최종 탈퇴]. 본인 재확인 없음.
  - 바로: 세션 폐기, 처리 중 새 여행·새 참여·새 이전 차단, MEMBER.STATUS=WITHDRAWN·DELETED_AT 기록, 남는 일정·메모 작성자 익명화(B), 본인 공개 게시물 비공개(D), 상세 처리 범위는 ACC-06-03 그대로.
  - 2주 보관, 2주 안에 재가입하면 여행까지 전부 복원(A-U02).
  - 2주 뒤: 개인 경비(D)·개인 체크리스트를 먼저 지우고 회원 행 삭제. 탈퇴로 삭제한 소유 여행도 이때 함께 영구 삭제(B의 휴지통 7일 자동 삭제에서 빠짐).
  - 처리 기록은 WITHDRAWAL_JOB, 소셜 연결 해제 실패는 재처리(ACC-06-04).

## 3. 접근 제어 (common/security)

- AccountStatusChecker: 로그인·탈퇴 처리 상태·이용 제한 판정. 이용 제한은 커뮤니티 변경 동작(PUB에서 열람 외)에만 적용. 제한 종료 시각이 지나면 job을 기다리지 않고 바로 해제로 판정.
- TripAccessChecker: 여행 ACTIVE·TRASHED 확인 + 현재 역할(OWNER / EDITOR / VIEWER). VIEWER는 조회만. 집 주소·개인 출발은 본인만. 조회 참여자는 공통·개인 경비 입력 불가. 권한을 닉네임으로 판정하지 않는다.
- AdminAccessChecker: MEMBER.SYSTEM_ROLE = ADMIN. 관리자는 서버 관리 절차로 미리 부여(가입·프로필로 승격 없음). 운영 조치 전 5분 안의 본인 재확인(서버 세션에 관리자 ID + 재확인 시각, `admin/service/ReauthService`).
- 거부 응답은 공통 형식으로, 거부 원인은 민감정보 없이 기록.

## 4. 참여자 규칙

- 초대 링크(COL-01): 여행당 활성 링크 1개, 발급 후 7일. 128비트 이상 무작위 토큰. 찾을 때는 해시(TOKEN_HASH), 다시 복사용으로 암호문(TOKEN_CIPHERTEXT, 키는 환경 변수). 폐기하면 행 삭제. 만료·폐기는 기존 참여자를 내보내지 않음.
- 초대 접속(COL-02-01): 로그인 전에는 여행 제목만, 일정·참여자 숨김. 로그인 후 여행명·도시·소유자 닉네임만 보여 주고 [참여하기]로 확정.
- 참여 등록(COL-02-02): VIEWER로 참여. 여행당 활성 참여자 최대 20명(소유자 포함). 참여 중인 활성 여행이 이미 3개면 참여 불가(B의 생성 개수 규칙과 같음). 소유자에게 참여 알림 1번.
- 역할 변경(COL-03-02): 소유자가 VIEWER <-> EDITOR. OWNER는 소유권 이전 수락으로만 바뀜. 열린 연결의 권한도 갱신(B).
- 나가기·내보내기(COL-04): TRIP_MEMBER 행 삭제 + 같은 트랜잭션에서 그 여행의 내 개인 경비(D)·개인 체크리스트(A)·개인 출발 정보(C) 삭제(11/23 결정, A-U03). 다시 참여하면 새 행(VIEWER), 지운 자료는 복구 없음. 내보낸 사람·시각은 기록하지 않음.
- 소유권 이전(COL-05): 대상은 현재 EDITOR. 여행당 PENDING 1건, 48시간. 요청자 취소·대상 거절, 만료·탈퇴·역할 상실·여행 삭제 때 무효(INVALID). 이용 제한만으로는 무효 안 됨. 수락하면 한 번에 OWNER 교체(받는 사람은 이미 참여 중이라 3개 상한 검사 없음). 공개 게시물 작성자·수정 권한도 새 소유자에게(D).

## 5. 운영 규칙

- 회원 목록(ADM-01-01): 검색어 1~100자, 최신 가입순 20개씩, 이메일 마스킹. 회원의 비공개 여행·일정은 볼 수 있지만 비밀번호 해시·외부 토큰·집 주소·개인 출발 정보는 볼 수 없음. 회원 정보·활동 화면을 열면 MEMBER_VIEW_LOG 기록.
- 이용 제한(ADM-01-02·03): 기간 1/3/7/30일, 근거 10~1,000자, 바로 시작. 사유: 스팸·광고 / 사칭 / 욕설·괴롭힘 / 개인정보 무단 게시 / 부적절한 닉네임 / 음란·불쾌한 내용 / 서비스 방해 / 기타. 자기 자신·다른 관리자 조치 금지, 활성 제한 중복 금지. 해제 사유 5~500자. 기간이 끝나면 `RestrictionExpireScheduler`가 해제. 대상 본인에게만 알림.
- 제한 안내(ADM-01-04): 커뮤니티에 들어갈 때 맨 위 안내 띠(사유·기간·[1:1 문의하기]). 문의 화면에는 제한 ID만 넘기고 유형을 '이용 제한 이의'로 미리 선택.
- 신고(ADM-02): 접수는 D(REPORT). 목록은 접수 오래된 순 20개, 처리 사유 5~500자. REPORT.STATUS = RECEIVED / DONE, REPORT_ACTION.DECISION = HIDE / DELETE / DISMISS / UNHIDE. 게시물은 관리자 비공개(D의 API로 ADMIN_HIDDEN), 댓글은 바로 삭제(복구 없음). 같은 대상의 다른 신고를 자동으로 완료하지 않음. 관리자 비공개 해제는 관리자 비공개만 풀고 소유자의 비공개 선택은 유지.

## 6. 알림 규칙 (NotificationService)

- 모든 파트가 이 서비스 하나로 알림을 저장한다. 같은 받는 회원 + 종류 + 대상 종류 + 대상 ID면 새 행을 만들지 않고 기존 행을 안 읽음으로, 만든 시각을 지금으로 바꾼다(UQ_NOTIFICATION_01).
- 본문 사본을 저장하지 않는다. 종류별 문구를 미리 정해 두고 보여 줄 때 채운다(`NotificationMessageMaker`). 접근 권한을 확인한 뒤 문구를 만든다.
- 받는 사람(A-P24): 참여 -> 소유자 / 역할 변경·내보내기 -> 대상 본인 / 일정 변경(방문 항목·후보·메모) -> 바꾼 사람을 뺀 활성 참여자 / 제한·해제 -> 본인 / 신고 결과 -> 신고자 / 게시물 관리자 비공개·해제, 댓글 삭제 -> 작성자 / 공개 댓글 -> 게시물 작성자(본인 댓글 제외) / 문의 최초 답변 -> 질문자(수정 답변은 다시 안 보냄). 참여가 끝난 사람에게는 여행 일정 알림을 보내지 않는다.
- 목록: 최신순 20개씩, [모두 읽음], 안 읽은 개수 배지 99+. 화면을 열어 둔 동안 새 알림이 오면 배지를 바로 갱신(B의 WebSocket 연결 사용). 공개 댓글 알림은 보여 줄 때 원문 앞 30자.
- 보관: 만든 시각 기준 30일, 읽음과 상관없이 하루 1번 삭제(`NotificationScheduler`).
- 저장 실패: 원래 동작은 성공으로 두고, 알림은 재시도 없이 운영 로그에 남긴다(A-P23, 11/23).
- B의 일정 변경 알림: TYPE = SCHEDULE_CHANGED, TARGET_TYPE = VISIT / CANDIDATE. 읽음 처리하면 B 화면의 바뀐 항목 점이 사라진다.
- 영구 삭제되는 여행의 알림을 지우는 메서드를 B에 제공한다(NOTIFICATION.TRIP_ID는 DB가 비우기만 함).

## 7. 원래 E 기능 규칙

- 보관함(PLC-04): 용어는 '즐겨찾기'('찜' 쓰지 않음). 회원당 500개, 같은 장소(제공자 + 장소 ID) 중복 불가. 저장 형식은 C의 공통 장소 형식. 하트 버튼 화면은 C, 저장·삭제는 A. 빼기는 확인 창 "보관함에 있는 장소예요. 삭제할까요?" -> [삭제]. 공동 후보에는 영향 없음. 목록은 담은 시각 최신순 10개씩, 필터 [전체] [국내] [해외], 카테고리 드롭박스, 장소 이름 검색. B의 '내 보관함에서 불러오기'에는 여행 도시와 같은 지도 제공자 장소만 준다.
- 날씨(SUP-01): Open-Meteo Forecast API(키 없음), 서버를 거쳐 호출, 도시별 1시간 서버 메모리 캐시(테이블 없음). 여행지 현지 오늘부터 16일 안만, 지난 날짜는 표시 안 함, 그 뒤는 "날씨 예보는 여행일 16일 전부터 제공돼요" 배지. 하루 값 그대로(최고·최저 기온, 최대 강수확률, 날씨 코드). 코드 아이콘: 0 맑음 / 1·2 구름 조금 / 3 흐림 / 45·48 안개 / 51~57 이슬비 / 61~67·80~82 비 / 71~77·85·86 눈 / 95~99 뇌우. 시간표 맨 아래 "날씨 정보: Open-Meteo". 공개 화면에는 표시 안 함.
- 체크리스트(SUP-02): 공동(ITEM_TYPE=SHARED) 여행당 200개, 개인(PERSONAL) 1인당 200개, 1~100자 한 줄. 정렬은 안 끝난 항목(항목 ID 순) 다음 완료 항목, 끌어서 순서 바꾸기 없음. 공동 항목 편집은 소유자·편집 참여자, 개인 항목은 주인 본인만(조회 참여자는 보기만, 모두가 모두의 개인 체크리스트를 봄). 공동 체크는 사람별(CHECKLIST_CHECK), 전체 인원 = 소유자 + 편집 참여자, 모두 체크하면 완료(IS_COMPLETED). 항목 내용 동시 수정은 나중 저장 우선, 체크는 사람별이라 덮어쓰지 않음. 변경 전파는 B의 SyncService. 공동 삭제는 확인 창, 개인 삭제는 바로.
- PNG 저장(SUP-04): 소유자·편집 참여자만. 화면에서 html2canvas로 만들고 서버에 저장하지 않음. 넣는 것: 제목·날짜·시간순 방문·이동 정보(대중교통이면 노선·환승·거리)·메모·숙소. 빼는 것: 집<->공항·경비·참여자·경고·환율·교통비·날씨·체류시간·지도.
- FAQ(ADM-03·04): 누구나 공개 FAQ 조회, 검색창 없음, FAQ ID 순. 관리자만 등록·수정·공개/비공개(삭제 없음), 새 FAQ는 비공개. 질문 2~500자, 답변 5~3,000자.
- 1:1 문의(ADM-05·06): 회원만(이용 제한 회원 포함). 유형 ACCOUNT / RESTRICTION / BUG / ETC, 제목 2~100자, 본문 10~3,000자, 같은 회원 1분에 1건. 답변 전에만 수정·삭제. 목록 10개씩. 관리자 목록은 답변 전 문의를 오래된 순으로. 답변은 문의당 1개(INQUIRY.ANSWER), 5~3,000자, 처음 등록할 때만 알림. FAQ·답변 동시 수정은 나중 저장 우선.

- 전체: AccountStatusChecker·TripAccessChecker·AdminAccessChecker, NotificationService, MEMBER_ID 기준 닉네임 조회(MemberService)
- B: ParticipantService(OWNER 등록, 참여 관계·역할 조회, 복원 시 소유자 외 참여자 삭제, 초대 링크 폐기), 여행 ID로 알림 삭제, 보관함 목록, 체크리스트 완료 수(메인 화면)

## 9. 문서끼리 다른 곳 (코드 쓰기 전에 사람에게 확인)

- 나가기·내보내기 때 개인 체크리스트: COL-04-01·02 기능 정의, A-U03, DB설계서 v7은 "삭제"(11/23), COL-04-02와 SUP-02-04의 협업 칸, 기준값 '내보내기 데이터 처리'에는 "남김"이 남아 있다. 이 파일은 삭제로 적었다.
- 알림 저장 실패: A-P23(11/23)은 "재시도 없이 운영 로그", 기준값 '알림 저장 실패'(11/05)는 "알림만 최대 3번 다시 시도". 이 파일은 A-P23으로 적었다.
- 신고 처리 결과 값: A-P21은 HIDE / DISMISS / TARGET_GONE, DB설계서 v7 REPORT_ACTION.DECISION은 HIDE / DELETE / DISMISS / UNHIDE. 이 파일은 DB설계서로 적었다.
- 프로필 사진·게시물 사진의 파일 형식·크기, 외부 메일 제공자는 아직 정하지 않았다.
